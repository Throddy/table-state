## 1. Цель

Для каждой строки `row_id` из `sample_submission.csv` (4733 строки, кадр × рамка стола) выдать пять счётчиков `people, hands, cups, dishes, items` и `occ_prob`.

Метрика (больше лучше):

```
score = 0.2 * AP(occupied, occ_prob) + 0.8 * mean_k max(0, 1 - WAPE_k)
WAPE_k = sum|y_k - pred_k| / sum(y_k)
```

Целевые отметки: 0.72 к пт 20:00 МСК, 0.78+ к сб 18:00 МСК. Финальный сабмит: сб 14.11.2026 23:59 МСК, внутренний стоп 22:30.

Следствия метрики, обязательные для всех:

1. WAPE это L1. Для каждой строки оптимален медианный ответ. Объект добавляется в счётчик, только если оценка вероятности того, что он настоящий и относится к этому столу, не ниже 0.5. Дробные счётчики допустимы только как результат усреднения ансамбля и только если это подтверждено валидацией.
2. Ложное срабатывание и пропуск стоят одинаково. Модуль, который на валидации даёт суммарную абсолютную ошибку больше суммы объектов класса, хуже нулей и выключается.
3. AP зависит только от порядка. `occ_prob` не округлять, не клипать в 0/1, избегать массовых совпадений значений.

## 3. Задача и определения счётчиков

Одна строка это одна рамка стола на одном целевом кадре. Рамка задаёт мебель, а не область отсечения.

| Поле | Считаем | Не считаем |
|---|---|---|
| `people` | сидящих за столом и стоящих вплотную к нему: гости, дети, персонал. Человек за дальней стороной столешницы относится к столу | прохожих в проходе |
| `hands` | видимые голые кисти над столешницей, каждую отдельно | кисти под столом, на коленях, в перчатках, у лица выше стола |
| `cups` | чашки, кружки, бокалы, стаканы, стаканы навынос на столе или в руке над ним | бутылки, банки, вазу с цветами |
| `dishes` | тарелки, миски, подносы, каждый предмет отдельно. Поднос с двумя тарелками = 3 | чашки, салфетки, еду без посуды |
| `items` | телефоны, сумки, кошельки, наушники, бумаги и другие личные вещи на столешнице, телефон в руке над ней | ноутбуки, планшеты, декор, игрушки, вещи на стуле/диване, одежду на спинке |
| `occ_prob` | уверенность, что `people > 0` | |

Дополнительно:

- Считаются только видимые объекты.
- Один объект относится ровно к одному столу. При неоднозначности выбирается стол, у которого он находится.
- На каждом столе стоит вазочка с сухоцветом. Это декор, в `cups` и `items` не входит. Все детекторы обязаны иметь для неё негативный класс или фильтр (см. 8.2).
- `table_id` это номер рамки слева направо внутри кадра, а не физический стол. В коде использовать `slot` (7.3).
- Строки нужны для всех `row_id` шаблона, даже если кадр не оценивается.

- Пути только через переменные окружения, никаких абсолютных путей в коде:
  - `TS_DATA` (по умолчанию `./data`)
  - `TS_ARTIFACTS` (по умолчанию `./artifacts`)
- Сид везде 419 (как в бейзлайне организаторов), если не указано иное. Для torch: `torch.manual_seed`, `cudnn.deterministic=True`, генерация VLM без сэмплирования.
- Веса моделей скачиваются скриптом `tracks/<трек>/fetch_weights.py` с зафиксированной ревизией (commit hash на Hugging Face или точное имя файла релиза). Во время инференса сеть не используется.
- Координаты во всех артефактах: пиксели исходного кадра 1280×720, формат `x1, y1, x2, y2`, float. Нормированные координаты aux переводить сразу при чтении.
- Время: в артефактах UTC. `hour_msk = (hour_utc + 3) % 24`.
- Имена классов в артефактах только из канонического словаря (8.2).

### 6.1 Kaggle как эталонная среда

Сабмиты и лидерборд на Kaggle, финалистов проверяют на соответствие кода сохранённому сабмиту. Поэтому эталонный прогон решения должен проходить в Kaggle Notebook, даже если разработка идёт локально.

- Данные соревнования в ноутбуке лежат в `/kaggle/input/<слаг соревнования>/`. Каталог ищется так же, как в `baseline.ipynb` организаторов (по наличию `train_labels.csv`, `tables.csv`, `data_card.json`), и записывается в `TS_DATA`. Слаг в коде не хардкодить.
- `TS_ARTIFACTS=/kaggle/working/artifacts`. Всё, что нужно сохранить между сессиями, выгружается как Kaggle Dataset.
- Общие артефакты команды это приватные Kaggle Datasets с доступом всем участникам: `ts-artifacts-dets`, `ts-artifacts-rowfeats`, `ts-models` (имена можно поменять, но зафиксировать в `README.md`). Новая версия артефакта это новая версия датасета, в карточке артефакта указывается номер версии.
- Веса моделей: сначала ищем готовую модель в Kaggle Models, иначе один раз скачиваем с Hugging Face скриптом `fetch_weights.py` (ноутбук с включённым интернетом) и публикуем как Kaggle Dataset. В `MODELS.md` указываются и исходная ссылка с ревизией, и имя датасета.
- Финальный инференс-ноутбук запускается с выключенным интернетом. Зависимости, которых нет в образе Kaggle, ставятся из колёс, лежащих в датасете (`pip install --no-index --find-links`).
- Квота GPU ограничена по аккаунту (обычно около 30 часов в неделю, точное значение смотреть в настройках аккаунта), сессия тоже ограничена по времени. Следствия: у каждого участника свой аккаунт и своя квота; долгие прогоны (VLM на 4733 строках) режутся на части с возобновлением и запускаются через Save Version (Run All), а не в интерактивной сессии; расход квоты каждый записывает в журнал.
- Интерактивная сессия Kaggle не переживает закрытие вкладки. Агент, который работает локально, готовит скрипты так, чтобы они запускались в ноутбуке одной ячейкой: `!python tracks/<трек>/<скрипт>.py ...`.

### 8.1 Детекции: `artifacts/dets/<source>__v<N>.parquet`

| Колонка | Тип | Смысл |
|---|---|---|
| `det_id` | str | уникален в файле, `<source>_<frame_id>_<n>` |
| `frame_id` | str | любой из 1718 основных кадров |
| `source` | str | имя источника |
| `class_name` | str | из словаря 8.2 |
| `confidence` | float | 0–1 |
| `x1, y1, x2, y2` | float | пиксели кадра 1280×720, `x2 > x1`, `y2 > y1`, в границах кадра |

- Покрытие: источник обязан обработать **все 1718 кадров** (или все строки `rows_ext`, если работает по кропам). Частичное покрытие допускается только с флагом `"coverage": "train_only"` в карточке и только для отладки.

## 9. Геометрия и привязка объектов к столам (`ts.assign`)

Значения ниже это стартовые настройки. A подбирает их на train в рамках раздела 12 и фиксирует в `configs/default.yaml`. Треки B и C привязку не реализуют, а отдают боксы.

### 9.1 Зоны стола

Пусть рамка стола `(x1, y1, x2, y2)`, `w = x2 − x1`, `h = y2 − y1`.

| Зона | Определение | Для чего |
|---|---|---|
| `top` | рамка, расширенная на 8% `w` и 8% `h` во все стороны | объекты на столешнице, руки над ней |
| `seat` | `x1 − 0.45w … x2 + 0.45w`, `y1 − 1.1h … y2 + 0.9h` | где находятся люди этого стола |
| `wide` | то же, что `seat`, обрезанное по кадру | кроп для VLM и для детекции людей |

Для слота 1 (у окна) и слота 6 (обрезан краем) зоны могут потребовать отдельных коэффициентов. Это единственное допустимое место для параметров, зависящих от слота.

Кропы для моделей:

- «узкий»: зона `top`, увеличение ×4 (примерно 740×500 px), для посуды, чашек, вещей, рук;
- «широкий»: зона `wide`, увеличение ×2.5–3, для людей и VLM.

### 9.2 Малые объекты (hand, cup, plate, bowl, tray, phone, bag, wallet, headphones, paper, personal_item)

1. Кандидат на стол: центр бокса лежит в зоне `top` этого стола.
2. Если центр лежит в зонах `top` двух столов, выбирается стол с большей долей площади бокса внутри его исходной рамки, при равенстве ближайший по расстоянию от центра бокса до центра рамки.
3. Объект вне всех зон `top` ни к какому столу не относится.
4. Для `hand` дополнительно: центр должен быть не выше `y1 − 0.05h` (кисть у лица выше стола не считается).
5. Для `bag` и `personal_item`: не меньше 60% площади бокса внутри зоны `top` (вещь на стуле или диване не считается).
6. Дедупликация между источниками и между кропами: детекции одного счётчика с IoU ≥ 0.5 (для боксов меньше 40 px: расстояние между центрами меньше 0.5 от меньшей стороны) считаются одним объектом.

### 9.3 Люди

1. Для каждого `person` и каждого стола считается оценка близости: доля площади бокса человека внутри зоны `seat` стола, умноженная на близость нижней трети бокса человека к рамке стола.
2. Человек привязывается к столу с максимальной оценкой, если она выше порога. Иначе это прохожий.
3. Фильтр прохожих: бокс, нижний край которого находится ниже `y2 + 1.2h` ближайшего стола и который не пересекается с его рамкой, считается стоящим в проходе.
4. Один человек относится только к одному столу.
5. Бейзлайн организаторов использует `пересечение / площадь стола ≥ 0.15`. Новое правило должно быть не хуже него на обоих фолдах, иначе остаётся бейзлайновое.

### 9.4 Объединение источников

Для каждого счётчика и строки из нескольких источников получается набор объектов после дедупликации 9.2.6. Объект получает оценку `p = f(источники, confidence)`, по умолчанию максимум калиброванных confidence, с бонусом за согласие двух и более источников. В счётчик входят объекты с `p ≥ thr_k`. Пороги `thr_k` (по одному на класс и источник) это основные подгоняемые параметры решения.

## 10. Контекст ±30 секунд (`ts.temporal`)

| Счётчик | Правило по умолчанию | Почему |
|---|---|---|
| cups, dishes, items | медиана счётчика по доступным кадрам (текущий + соседи); при одном соседе берётся максимум из двух, только если оба больше 0, иначе текущий | объекты статичны, медиана гасит разовые пропуски и ложные |
| hands | только текущий кадр | руки двигаются; максимум по соседям на train роняет качество с 0.586 до 0.414 |
| people | текущий кадр; если на текущем 0, а на обоих соседях одинаковое число больше 0 и на текущем есть руки или низкоуверенный `person` в зоне, берётся значение соседей | человек за 30 секунд обычно не исчезает, но мог быть пропущен |
| occ_prob | признаки текущего кадра и обоих соседей | |

Дополнительно для статичных классов можно сопоставлять сами объекты между кадрами (тот же класс, центр сместился меньше чем на 12 px): объект, который есть на двух из трёх кадров, получает бонус к `p`.

Отсутствующий сосед это штатная ситуация. Код не должен падать и не должен подставлять нули вместо отсутствующего кадра.

## 11. Стекер и постобработка (`ts.stack`, `ts.post`)

### 11.1 Счётчики

Базовая форма: для каждого класса правило «число объектов с `p ≥ thr`», пороги подбираются на train по сетке с шагом 0.05, критерий: суммарная абсолютная ошибка класса. При равенстве выбирается порог, который устойчивее (плато), а не край.

Разрешено усложнение только при выполнении раздела 12.3: линейная или GBM-модель с не более чем 6 признаками на класс и `min_samples_leaf ≥ 5`. Глубокие модели на 231 строке запрещены.

VLM-счётчики входят как источник голосования: итог по классу это медиана из (детекторный счётчик, VLM-счётчик, контекстная медиана), если VLM прошёл проверку 13.C3.

### 11.2 `occ_prob`

Логистическая регрессия (L2, `C` подбирается из `{0.1, 1, 10}`) на признаках: число людей по каждому источнику (текущий кадр и соседи), максимум confidence `person` в зоне `seat`, число рук, число чашек, VLM `people`, `slot`, `is_ir`. Выход не округляется. Гарантии:

- если итоговый `people ≥ 1`, то `occ_prob ≥ 0.5 + 0.01·min(people, 5)` (поднимаем, не нарушая порядок внутри группы);
- к `occ_prob` добавляется детерминированный микросдвиг `1e-6 · rank(признаки)` для разрыва совпадений.

### 11.3 Постобработка (каждое правило включается флагом и проверяется отдельно)

| Флаг | Правило | Основание |
|---|---|---|
| `hands_need_people` | если `people = 0`, то `hands = 0` | в train рук без человека нет |
| `hands_cap` | `hands ≤ 2·people` | |
| `round_counts` | округление до целого | L1-оптимум целочисленный |
| `clip` | счётчики в `[0, 50]`, `occ_prob` в `[0, 1]` | валидатор организаторов |
| `empty_night` | не включать без проверки | в тесте есть ночные компании (см. выброс 4.4) |

Запрещено: правила вида «если слот 4, то 0» (в train слот 4 пуст случайно, в тесте детектор видит там людей), любые правила по `frame_id`, `row_id`, по времени суток без проверки на обоих фолдах.

## 12. Валидация

### 12.1 Схема

- `f25`: подгонка на 25.10, проверка на 26.10 (105 строк). Это официальная схема организаторов.
- `f26`: подгонка на 26.10, проверка на 25.10 (126 строк).
- `oof_all`: объединённые out-of-fold предсказания двух фолдов, оценённые один раз на всех 231 строках. **Основная локальная метрика.**
- Для чистого zero-shot `oof_all` это просто оценка на всех 231 строках.

Кадры 25.10 и 26.10 не смешиваются. Соседи train-кадров того же дня можно использовать как контекст и для псевдоразметки, но не как размеченные примеры в другом фолде.

### 12.2 Что обязан содержать отчёт `ts.cv.evaluate`

- `score`, `occupancy_ap`, качество по каждому из пяти классов, `abs_error` и `objects` по классам: для `oof_all`, `f25`, `f26`.
- То же без кадра-выброса `im_cf13426b6f011b9cb35c` (вид «robust»).
- Отдельно по `is_ir = 1` и `is_ir = 0`.
- Bootstrap по кадрам (1000 повторов): 5-й и 95-й перцентили `oof_all`.
- Число подгоняемых параметров.

### 12.3 Правило принятия изменения

Изменение принимается в основной конфиг, если одновременно:

1. `oof_all` вырос не меньше чем на 0.010;
2. ни один из фолдов не упал больше чем на 0.010;
3. вид «robust» не упал;
4. при сдвиге каждого нового порога на ±20% выигрыш сохраняет знак.

Если выполнены не все пункты, изменение остаётся кандидатом и может быть проверено сабмитом (решает A). Выигрыш меньше 0.02 только на Public и без локального подтверждения не принимается.

### 12.4 Источники, обученные на кадрах train-дней

Если детектор обучался на псевдобоксах кадров 25–26.10, его счётчики на этих же кадрах завышены. Для таких источников:

- либо обучаются две версии (без кадров 25.10 и без кадров 26.10), и на train-строки каждого дня идут детекции той версии, которая этот день не видела; финальная версия на всех данных применяется к тесту;
- либо источник оценивается только сабмитом и по aux-holdout (5–8 aux-кадров, отложенных от обучения), а в `oof_all` участвует с пометкой «leaky».

Псевдоразметка тестовых дней на валидацию не влияет и разрешена без ограничений.

### 12.5 Проверка заменой колонки на Public

Локальная оценка на 231 строке (23 занятые) не годится для выбора между близкими вариантами: первые сабмиты показали обратный порядок на Public (4.5). Поэтому:

1. Метрика аддитивна по колонкам. Изменение колонки (`occ_prob`, `people`, `hands`, `cups`, `dishes`, `items`) принимается в основной сабмит только после проверки заменой: `python tools/swap_cols.py` подставляет эту колонку в лучший на данный момент файл, и результат подтверждается на Public.
2. Разница меньше 0.01 Public по колонке считается ничьёй. При ничьей остаётся вариант бейзлайна организаторов (или тот, что уже стоит в лучшем файле).
3. Локальная оценка по 12.2 остаётся обязательной как фильтр: вариант, который локально хуже нулей или хуже бейзлайна на обоих фолдах, на Public не тратится. Правило 12.3 теперь означает «кандидат на проверку сабмитом», а не «принято».
4. Бюджет отправок ограничен (раздел 14), поэтому близкие по смыслу изменения одной колонки проверяются одним сабмитом, а каждая запись журнала о замене колонки содержит имя базового файла.

- Отправляет только A, командой `python tools/submit_gate.py --pred artifacts/preds/<name>.csv --note "<один вопрос, на который отвечает сабмит>"`.
- `submit_gate` делает: `ts.check_pred`; оставляет только 4733 тестовые строки в порядке шаблона; проверку валидатором `score.validate_submission`; проверку, что `occ_prob` имеет не меньше 200 уникальных значений; сохраняет `submissions/<name>.csv`, `<name>.json` (git sha, конфиг, локальные метрики 12.2, список источников) и копию конфига в `configs/submissions/`.
- Отправка на Kaggle: через Submit Prediction на странице соревнования или `kaggle competitions submit -c <слаг> -f submissions/<name>.csv -m "<name> <git sha>"`. В описании отправки всегда имя и git sha, чтобы любой сабмит на Kaggle однозначно находился в `submissions/`.
- После отправки A дописывает в карточку `public_lb` и строку в журнал.
- Лидерборд и Private считаются только на Kaggle. Локальные цифры нужны для решений, а не для отчётности о месте.
- Бюджет: не больше 8 в день, 2 в резерве. Последняя отправка сб 22:30 МСК.
- Финальные две: `S_safe` (лучший по `oof_all` и «robust», консервативные пороги) и `S_bold` (лучший Public при условии, что локально не хуже `S_safe` больше чем на 0.01). Выбор фиксируется в журнале с обоснованием.
- Уточнение от 13.11: на Kaggle сейчас можно выбрать только 1 финальную отправку. Вопрос организаторам задан. До ответа считаем, что финальный сабмит один и это `S_safe`; `S_bold` готовится как запасной на случай, если разрешат две.
- Две финальные отправки отмечаются вручную на странице Submissions соревнования до сб 22:30 МСК. Если не отметить, Kaggle сам возьмёт лучшие по Public, а это может быть не `S_safe`. После отметки A делает скриншот и кладёт в `report/`.

## 15. Воспроизводимость и отчёт

### 15.1 Единая команда

```bash
python run.py --data $TS_DATA --artifacts $TS_ARTIFACTS --config configs/submissions/<name>.yaml --out submission.csv
```

Этапы `run.py` (каждый можно пропустить флагом `--from-cache`, если артефакт уже есть и его sha совпадает с карточкой):

1. `build_rows_ext`
2. инференс источников (`tracks/det/infer.py`, `tracks/ov/run_*.py`) → `dets/`, `rowfeats/`
3. `assign` → `temporal` → `features`
4. `stack.fit` на train-счётчиках → `predict` на тесте
5. `post` → `submission.csv` → `ts.check_pred`

Эталон воспроизведения: ноутбук `notebooks/final_inference.ipynb` на Kaggle (интернет выключен, подключены датасет соревнования и датасеты команды с весами и кодом), который вызывает ту же команду `run.py` и пишет `/kaggle/working/submission.csv`. Сдаётся ссылка на ноутбук и архив репозитория.

Обучение детектора (трек B) вынесено в отдельную команду `python tracks/det/train.py --config ...`, веса прикладываются. В отчёте указывается и команда обучения, и команда инференса.

## 16. Правила работы агентов

1. Перед началом: прочитать `CONTRACT.md`, раздел своего трека, последние 30 строк общего журнала (`python tools/log_all.py --tail 30`), `experiments/ORG_ANSWERS.md`.
2. Работать только в своей зоне владения (раздел 5). Чужие файлы не править.
3. Любой артефакт: файл + карточка + `ts.check` + строка в журнале своего трека (`experiments/LOG_<трек>.md`). Без этого работа не считается сделанной. В чужие журналы и в `experiments/LOG.md` агент не пишет.
4. Не выдумывать числа. Любая метрика в журнале получена запуском `ts.cv.evaluate` или `tools/eval_pred.py`, команда указана.
5. Не подгонять по тесту. Тестовые кадры открывать только для отладки визуализации и демо.
6. Не использовать закрытые API и модели в коде решения. Если библиотека по умолчанию ходит в сеть (телеметрия, автозагрузка весов), отключить и зафиксировать веса.
7. Не увеличивать число подгоняемых параметров без нужды. Каждый новый параметр указывается в отчёте эксперимента.
8. При расхождении с фактами раздела 4 сначала искать ошибку у себя.
9. Долгие прогоны (больше 20 минут) делать с контрольными точками и возобновлением: запись результата порциями, пропуск уже обработанных строк.
10. Если задача блокируется больше чем на 30 минут, записать блокер в журнал и переключиться на следующую задачу трека.
11. Перед каждой контрольной точкой (пт 14:00, 20:00, 23:00; сб 12:00, 15:00, 18:00 МСК) подготовить человеку сводку из 5 строк: что готово, цифры, что не получилось, что дальше, что нужно от других.
12. Изменения контракта только через `experiments/PROPOSALS.md` и решение A.
13. Коммиты, пуши и pull request агент делает сам, но строго по правилу R6: никаких `Co-Authored-By`, «Generated with/by», почты или имени ИИ, ссылок на сессии. Перед каждым пушем агент проверяет `git log -n 20 --format='%an <%ae>%n%B'` и убеждается, что там нет таких строк и что автор это владелец трека. Если приписка попала в непушнутый коммит, он исправляется через `git commit --amend` или `git rebase` до пуша. Если она уже в удалённой ветке, агент останавливается и сообщает человеку, а историю сам не переписывает.
14. Сообщения коммитов короткие и по делу, в повелительном наклонении, с префиксом трека: `core: ...`, `det: ...`, `ov: ...`.
